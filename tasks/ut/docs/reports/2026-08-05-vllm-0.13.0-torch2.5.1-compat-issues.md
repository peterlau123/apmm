## 2. 问题详情

### 2.1 🔴 illegal memory access —— **GPU 1 卡硬件异常**（403 个，非 kernel bug）

**症状**：`test_fused_quant_layernorm.py::test_rms_norm[cuda:1-...]` 单独运行报：

```
E RuntimeError: CUDA error: an illegal memory access was encountered
E AssertionError: assert False  (allclose 数值不对)
```

**🔬 深究根因（2026-08-05，compute-sanitizer + 双卡对照实验）**：

**决定性证据：同一 kernel、同一形状，cuda:0 正常 / cuda:1 崩溃**

| 实验 | 结果 |
|---|---|
| cuda:0 单独跑 `per_token_group_quant_int8`（[1,1024] bf16, group=64） | ✅ OK 无越界 |
| **cuda:1 单独跑同一 op（同形状）** | 💥 `Invalid __global__ read`（input 指针悬垂，负 768MB 偏移） |
| `test_rms_norm[cuda:0-...-1-1024]`（cuda:0 参数化） | ✅ **1 passed, 1.97s** |
| cuda:0 抽样 7 组组合（h=64/1024/5120 × group 64/128/None × int8/fp8 × residual） | ✅ **5 passed**（2 组 0-tests 为测试自身条件） |
| nvidia-smi 卡 1 | ECC=0 / 温度正常（表面正常，但 kernel 访问悬垂内存） |

**结论（更正）**：
- ❌ 早前推测"vllm kernel vectorized 路径越界"**错误**——cuda:0 上 hidden 对齐（1024/5120）照样 passed
- ❌ "hidden 16 对齐规律"是假象——非对齐组合（h=1025/1027/1029/5137）因测试开头
  `hidden_size % group_size != 0` 提前 `return` **假通过**（kernel 未执行）
- ✅ **真实原因：H20 物理卡 1（GPU 1）显存寻址异常**——非法内存访问（可能硬件
  故障/驱动问题，ECC 未报但 compute-sanitizer 证实访问悬垂内存）。涉及 kernel
  `per_token_group_quant_8bit_kernel`（csrc/quantization/w8a8/fp8/per_token_group_quant.cu）
  在 cuda:1 上读 input 悬垂指针

**影响**：403 个 `fused_quant_layernorm` 用例 **device 参数全部固化在 cuda:1**
（Phase 1 generate_batch 收集时固化的 CUDA_DEVICES 前 2 卡，但用例实际都选了
cuda:1）→ 全部因卡 1 异常崩。
**性质**：**环境/硬件问题，非 vLLM 代码缺陷**（kernel 在健康卡上全过）。
**处置（已执行，2026-08-05 下午）**：
1. ✅ **device 映射重跑完成**：`retry_kernel_tests.py --device-map cuda:1=cuda:0`
   （运行层映射到健康卡 0，回写原 cuda:1 节点）——**400 个全部 passed**
   （0 failed / 0 error），fused_quant_layernorm 405 个用例全部验证通过
2. ✅ **execute_batch 加 `exclude_gpus` 配置**（commit `4001fef`）：
   workflow.yaml `exclude_gpus: [1]`，后续跑测试自动避开卡 1
3. ⏳ 卡 1 硬件诊断（`nvidia-smi -r` 重置 / 驱动排查 / 换卡）——用户稍后处理

### 2.2 🟡 CUDA_VISIBLE_DEVICES 单卡 → 参数化节点 not found（559 个）

**症状**：execute_batch 重试时报 `ERROR: not found: test_reshape_and_cache[...]`
→ pytest 收集 0 → ignored。看起来像死测试，**实际不是**。

**根因（对照实验证实）**：
```
A: pytest --collect-only "<node>"                      → 1 test collected ✅
B: CUDA_VISIBLE_DEVICES=0 pytest "<node>"              → ERROR: not found ❌
C: pytest "<node>"（不设 env）                          → 1 passed, 2.2s ✅
```
vllm kernel 测试参数化 `cuda:1-...` 依赖**运行时可见 GPU**：设单卡后只生成
`cuda:0` 节点，命令行传的 `cuda:1` 节点匹配不上 → not found。
execute_batch 对 normal 测试硬编码 `CUDA_VISIBLE_DEVICES={gpu_id}`，恰好触发。

**影响**：`test_cache.py` 391 个 + `test_prefix_prefill.py` 168 个 = **559 个
可救**（不设 env 单独跑全部 passed，2.2-2.9s/个）。
**性质**：执行框架问题（非 vLLM 代码缺陷），但暴露了 **vllm 参数化依赖
GPU 可见性**的设计特性。
**处置**：串行重跑（不设 CUDA_VISIBLE_DEVICES）可全部救回，已计划执行。

### 2.3 🟡 Server failed to start in time（~50 个）

**症状**：`RuntimeError: Server failed to start in time.`（vLLM server 启动
241s 超时被杀）。涉及 `test_async_tp_pass_correctness`、
`test_attn_quant` 等 distributed 测试。

**验证**：重试后这些测试稳定 failed（非偶发）。torchrun 2 卡 + TinyLlama/
NVFP4 模型加载 + server 启动在 600s watchdog 内无法完成或启动失败。
**性质**：测试重量级（真实模型加载）+ server 启动在 H20 上偏慢，疑似
**资源/启动路径问题**，需单测定位是启动慢还是启动失败。

### 2.4 🟡 torch.compile 分布式重活超时（48 个）

**症状**：`test_sequence_parallelism_pass` 15 个参数化 XML 实测 19-20min
（max 20.4min），远超 600s watchdog；`test_shm_broadcast` 1 个实测 **60min**
（疑似卡死非慢）。

**验证**：XML time 属性实测（非猜测）。
**性质**：torch.compile + 分布式 AllReduce 大张量（16x16x8）重活，**性能级
超时**。提高 watchdog 到 1800s 可跑但代价大，且 shm_broadcast 60min 疑似
卡死（SHM 广播等待）。
**处置**：已从重试队列剔除（慢测试清单），单独 `--timeout 1800` 单跑或
接受 ignored。

### 2.5 🟢 并发导入竞争 → pytest 收集 0（偶发）

**症状**：多 worker 并发执行时 `JUnit XML has no <testcase> (pytest aborted
pre-result)`，单独 collect-only 全部 `1 test collected`。

**性质**：环境冲突（vllm/triton/flashinfer 导入竞争），非版本问题。
**处置**：v5 自动重试（MAX_RETRIES=3）已覆盖；kernel 串行重跑（2.2 节）
将彻底规避。

### 2.6 🔴 分布式初始化崩溃 ProcessRaisedException（慢测试 19 个，2026-08-05 夜）

**症状**：慢测试单跑（`--slow-only --timeout 1800`）时
`torch.multiprocessing.spawn.ProcessRaisedException`——子进程在
`init_distributed_environment()` 崩溃（NCCL/环境初始化失败）。

**数据**：64 个已执行慢测试中 37 failed，其中 **19 个 ProcessRaisedException**
+ **4 个 `Engine core initialization failed`**（vLLM engine 初始化失败）。

**特征**：同文件同参数族的变体部分通过（如 batch 222609: 6p/2f），部分崩
（231854: 0p/6f/2ig）——**疑似参数化变体差异 + 环境 flaky**（分布式初始化
时序、NCCL 建连、GPU 池非连续 [0,2,3] 影响部分场景）。
**性质**：分布式测试在 H20 上的初始化稳定性问题（非确定性失败）。
**处置**：已止损（同型失败率 ~58%，剩余 30 个未跑）；建议单测复现 + 排查
NCCL 初始化日志。

## 4. 慢测试耗时分析（为什么 64 个跑了 14 小时）

慢测试单跑（`--slow-only --timeout 1800`）64 个测试耗时 14h（平均 ~13min/个，
super batch 内 2 并发），耗时构成：

| 耗时来源 | 占比 | 说明 |
|---|---|---|
| **torch.compile 即时编译** | ~60% | 每个测试独立编译模型（4×RMSNorm + 3×Linear + all_reduce 算子链，vllm 自定义 TestBackend AOT 编译 + Triton kernel 生成），**10-20min/次**，参数化变体间不共享编译产物 |
| **大模型加载** | ~20% | attn_quant 类：Qwen3-0.6B / RedHatAI Llama-3.1-8B NVFP4 真实权重从 HF 缓存加载（数 GB）+ 量化转换 + tp2 张量并行 |
| **分布式开销** | ~10% | 每测试 `run_torch_spawn` 2 进程 torchrun + NCCL 建连（含失败重试/超时） |
| **watchdog 上限效应** | ~10% | 多个测试跑到 1800s 上限被杀（shm_broadcast 60min 卡死、部分编译超时） |

**结论**：耗时是**测试设计使然**（验证 torch.compile 融合 + 量化正确性 =
编译重活），非执行框架问题。优化方向：① torch.compile 编译产物跨变体缓存；
② 参数化变体抽样（48 个 sequence_parallelism 变体结构高度相似）；③ 分布式
初始化失败快速重试。

## 5. 结论与建议

1. **没有确凿的 vLLM 0.13.0 + torch 2.5.1 代码级兼容性 bug**——403 个
   fused_quant_layernorm "illegal memory access" 经 compute-sanitizer 双卡对照
   证实是 **GPU 1 卡硬件异常**（非 kernel bug，device 映射到 cuda:0 全部通过）
2. **559 个 test_cache/prefix_prefill 是执行框架问题**（CUDA_VISIBLE_DEVICES
   单卡 → 参数化节点 not found），串行重跑全部救回，非 vLLM 缺陷
3. **分布式初始化稳定性问题**（ProcessRaisedException 19 个 + Engine init 失败
   4 个）：慢测试在 H20 上的非确定性初始化失败，需单测复现 + NCCL 日志排查
4. **性能级超时**（sequence_parallelism torch.compile 20min+ / shm_broadcast
   60min 疑似卡死）：测试设计重活，需评估接受 failed/ignored 或优化编译缓存
