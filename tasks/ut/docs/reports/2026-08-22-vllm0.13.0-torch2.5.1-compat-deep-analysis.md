## 1. 兼容性问题总结分析（核心章节）

### 1.1 总体结论

| 类别 | 数量 | 占比(非passed) | 性质 |
|---|---|---|---|
| **A. 版本配套兼容性问题** | **2,122** | 34.9% | vllm 0.13.0 与 torch 2.5.1 / triton 3.5.0 不配套，**与芯片无关** |

### 1.2.1 marlin 算子缺失根因证据链（已验证，非推测）

1. **现象**：`NotImplementedError: Could not run '_C::gptq_marlin_gemm' with arguments from the 'CUDA' backend`（479 条）+ `gptq_marlin_repack`（292 条）+ opcheck 相关（64 条）≈ 841 条
2. **验证 1 — 二进制符号**：`nm -D vllm/_C.abi3.so | grep -ic marlin` → **0 个 marlin 符号**
3. **验证 2 — 构建配置**：`CMakeCache.txt` 中 `CMAKE_CUDA_ARCHITECTURES:STRING=52`（sm_52），而 marlin 编译条件为 `MARLIN_ARCHS = 8.0+PTX ∩ CUDA_ARCHS`，**sm52 与 8.0+PTX 交集为空 → marlin 内核 0 个编译**
4. **验证 3 — H20 架构**：`nvidia-smi` 显示 H20 compute_cap = **9.0**（sm_90），在 marlin 支持范围内（8.0+），即**芯片支持但构建产物缺失**
5. **验证 4 — 构建时间**：`_C.abi3.so` 构建于 5 月 12 日（vllm 0.13.0 原始 wheel 打包），`_moe_C.abi3.so` 8 月 7 日重编后 moe marlin 失败从大量降至 4 条——印证「重新编译即可解决」
6. **结论**：**不是芯片不支持，是构建时 CUDA arch 配置错误（sm52）导致 marlin 内核被跳过**。修复 = 用 `TORCH_CUDA_ARCH_LIST="9.0"` 重新编译 vllm 扩展。**修复难度 easy，收益 841 条。**

### 1.2.2 triton_key 接口不兼容证据链（已验证）

1. **现象**：`ImportError: cannot import name 'triton_key' from 'triton.compiler.compiler'`（495 条，另 24 条带 `target: aten._scaled_mm.default`）
2. **验证**：容器内实测 `from triton.compiler.compiler import triton_key` → **复现同样 ImportError**
3. **环境**：容器 triton 3.5.0，python3.12
4. **归因**：vllm 0.13.0 的 torch.compile 路径引用 `triton_key`，但 triton 3.5.0 已重构该接口（更早/更晚版本均无）。**这是 triton 版本与 vllm 0.13.0 不配套**，非芯片问题。
5. **修复方向**：① 锁定与 vllm 0.13.0 配套的 triton 版本（如 3.2.x/3.3.x）；② 或 patch vllm 代码适配新接口（涉及 torch.compile 路径，改动面较大）。**修复难度 medium。**

### 1.2.3 cat_cuda Float8 未实现

- 225 条，集中在 `test_batched_moe.py`（192）+ `test_cutlass_w4a8_moe.py`（17）+ `test_flashinfer.py`（12）
- 错误：`RuntimeError: "cat_cuda" not implemented for 'Float8_e4m3fn'`
- 归因：torch 2.5.1 的 `torch.cat` CUDA 内核不支持 FP8（Float8_e4m3fn）数据类型——torch 2.5.1 对 FP8 的支持不完整。**这是 torch 版本能力边界**，升级 torch 或改代码路径（先转 bf16 再 cat）可解。**修复难度 medium。**

### 1.2.4 torch.float8_e8m0fnu 缺失

- 80 条，`AttributeError: module 'torch' has no attribute 'float8_e8m0fnu'`
- 归因：`torch.float8_e8m0fnu` 是 torch 2.7+ 新增的 8 位浮点格式（E8M0），2.5.1 不存在。vllm 0.13.0 代码已引用该类型（跟随上游 torch 演进）。
- 含义：**vllm 0.13.0 部分代码已经依赖 torch 2.7+ 的 API**，说明 vllm 0.13.0 实际要求 torch 版本高于 2.5.1。这是「vllm 0.13.0 + torch 2.5.1 不配套」的最直接证据之一。**修复难度 difficult**（2.5.1 下无此类型，只能条件兼容或升级）。

## 3. 除兼容性问题外需要关注的问题

1. **构建链 arch 配置错误（最优先）**：`_C.abi3.so` 用 sm52 编译导致 marlin 内核全缺失。这是**构建/发布流程缺陷**，不升级 torch 也应修复（重新编译即得 841 条）。建议检查 CI/打包脚本中 `CMAKE_CUDA_ARCHITECTURES` / `TORCH_CUDA_ARCH_LIST` 的来源。
2. **triton 版本锁定缺失**：容器 triton 3.5.0 与 vllm 0.13.0 不配套（缺 triton_key）。建议在容器/环境声明中锁定与 vllm 版本匹配的 triton 版本。
3. **HF 模型离线准备不完整**：29 个模型缺失导致 ~1,300 条失败（非兼容性）。建议：① 补齐 gated 模型授权（meta-llama 等需 token）；② 未授权模型用 `model_replacement.py` 替换；③ 建立模型缓存完整性检查。
4. **executor timeout 机制**：1,787 条 timeout 连坐中 detokenize 占 902。bifrost 180s 假活 + watchdog SIGKILL 导致「真超时」与「假超时」混杂。建议区分：真超时（用例本身慢）vs 假超时（executor 层问题），后者重跑可救。
5. **多卡测试环境**：17 条 `test_hybrid_lb_dp`/`test_internal_lb_dp` 需要多机/多卡，单机无法覆盖——环境限制，非代码问题。
6. **retriable_error 命令构造 bug**：3 条因 pytest_full_cmd 含单引号被 bash -c 破坏——框架命令构造缺陷，建议修（属 apmm 框架而非 vllm）。
7. **GPU 1 硬件异常残留**：历史 run 中 GPU1 Xid31/illegal memory access（已 exclude_gpus=[1] 规避），若换卡未确认，剩余少量 CUDA 类错误可能受此影响（本轮 8 条 cuDNN + 少量 CUDA error 需在健康卡上复验）。

## 5. 报告小结：兼容问题总体评估与升级建议

### 5.1 总体评估

| 维度 | 评估 |
|---|---|
| 通过率 | 26,875 / 32,955 = **81.5%**（passed） |
| 非 passed | 6,080（18.5%），其中**核心兼容性问题 2,122（34.9%）** |
| 兼容性问题性质 | **非芯片问题**：marlin 构建缺失（arch 配置错误）+ triton 版本不配套 + torch 2.5.1 能力边界（FP8 不完整） |
| 可救性 | 兼容性问题中：easy 修复 ~1,043（marlin 841 + deep_gemm 133 + triton 69）≈ 49%；medium ~550（triton_key 519 + head_size 64 等）；difficult ~80（float8_e8m0fnu） |
| 环境类 | 1,301 条补模型缓存即可救（非兼容性） |
| timeout 连坐 | 1,787 条重跑可救大部分（非兼容性） |

### 5.2 是否升级 torch？

**建议：有条件地升级，或至少修复构建问题后再评估。**

**支持升级（torch 2.6+/2.7+）的理由**：
1. **vllm 0.13.0 代码已引用 torch 2.7+ API**：`torch.float8_e8m0fnu`（80 条失败）在 2.5.1 中不存在——说明 vllm 0.13.0 实际开发基线已高于 torch 2.5.1
2. **torch 2.5.1 FP8 支持不完整**：`cat_cuda` 不支持 Float8_e4m3fn（225 条）——FP8 是 H20 关键能力（H20 是 FP8 训练/推理主力卡），2.5.1 的 FP8 内核覆盖不足是硬伤
3. **上游 vllm 已要求 torch 2.11.0**（main 分支 requirements）——vllm 官方已彻底离开 torch 2.5.x 时代，长期停留在 2.5.1 意味着无法跟进上游修复
4. **triton 配套问题**：torch 2.5.1 锁定的 triton 版本与 vllm 0.13.0 不匹配（triton_key 缺失），版本矩阵越老越难对齐

**支持暂不升级（维持 2.5.1）的理由**：
1. **marlin 841 条是构建问题不是版本问题**——重新编译即可解决，无需升级
2. **环境类 1,301 + timeout 1,787 + 可重试 5 ≈ 3,093 条与 torch 版本无关**——补模型 + 重跑即可，升级不解决它们
3. 目标芯片若已有基于 2.5.1 的算子/框架适配（如 deep_gemm 厂商版本），升级需重新验证全部配套

### 5.3 行动建议（优先级排序）

| 优先级 | 行动 | 预计收益 |
|---|---|---|
| P0 | **用 `TORCH_CUDA_ARCH_LIST="9.0"` 重新编译 vllm 扩展**（修复 marlin） | +841 条 |
| P0 | 锁定/安装与 vllm 0.13.0 配套的 triton 版本（或 patch triton_key 接口） | +519 条 |
| P1 | 补齐 HF 模型缓存（含 gated 授权）或用替代模型 | +~1,300 条 |
| P1 | 修复 executor timeout 机制（区分真假超时，加大 detokenize 类 timeout） | +~1,500 条 |
| P2 | 评估 torch 2.6/2.7 升级（重点验证 FP8 能力：cat_cuda/float8_e8m0fnu） | +~305 条兼容性 |
| P2 | 人工处理留存的 ~690-790 条（断言/空消息/杂项） | 定性收尾 |

**一句话结论**：`vllm 0.13.0 + torch 2.5.1` 在 H20 上的兼容性问题**约 1/3 是构建与版本配套缺陷（可低成本修复），约 1/4 是 torch 2.5.1 自身能力边界（FP8 不完整、缺 2.7 API）**；若目标芯片对 FP8 有硬需求，建议**升级 torch 至 2.6+（或跟随 vllm 官方版本）**，同时无论是否升级都需先修复 marlin 构建问题。
